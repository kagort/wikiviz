# ТЗ: завершение Phase 6 (WikiViz)

Документ для Claude Code. Владелец проекта работает с репозиторием `kagort/wikiviz` (ветка `main`) с двух Windows-компьютеров. Он доктор философии, не программист: отчёты пишем простым русским языком, без лишнего жаргона, объясняем «зачем», а не только «что». Ответственность за архитектурные решения остаётся у владельца (см. раздел 4.4).

## 4. Правила работы

### 4.1. Архитектура (не нарушать)

- `Extraction ≠ Transformation ≠ Visualization`. Логика извлечения не попадает в React, логика отображения не попадает в extractor.
- Rule 3: HTML Wikipedia не является контрактом. `Section` не содержит HTML.
- Rule 4: не создавать отдельные модели данных под конкретный виджет.
- Rule 5: новые данные сначала попадают в нормализованную модель (Pydantic в `backend/app/models/` и TypeScript в `frontend/types/`, синхронно, вручную).
- Rule 6: виджеты подключаются через `widgetRegistry` одной строкой в `lib/widgets/setup.ts`. `registry.ts` и `selector.ts` не менять.
- Контракт `Widget`: `id`, `name`, `version`, `description`, `supports(data)`, `render` (React-компонент, не функция).
- Extractors принимают простую строку HTML, а не Wikipedia-специфичный объект. Модуль `app/wikipedia/` не расширять сверх четырёх файлов (`client.py`, `models.py`, `errors.py`, `endpoints.py`).

### 4.2. Процесс

1. **Разведка перед кодом.** Гипотезы о разметке Wikipedia в этом документе не проверены. Сначала смотрим настоящий HTML (разведочный скрипт в `backend/scripts/`), потом пишем код. Проверка на обоих языках (en и ru) обязательна для всего, что читает HTML.
2. **Regression-тест до исправления.** Сначала тест, воспроизводящий баг, убедиться что он красный, потом исправление.
3. **Проверки всегда раздельно и с подсчётом:** `pytest` (backend), `npx tsc --noEmit`, `npm test`, `npm run build` (frontend). Jest не проверяет типы, поэтому зелёные тесты не заменяют `tsc`. В отчёте указывать число тестов до и после. Тесты не ослаблять и не удалять ради зелёного результата.
4. **Один логический шаг — один коммит**, коммитить только при полностью зелёных проверках. Без `push --force` и без переписывания истории.
5. Тесты офлайн. Скрипты с реальной сетью лежат в `backend/scripts/`, запускаются `python -m scripts.<name>`, в `pytest` не попадают (в них не должно быть функций `test_*`).
6. Временные дампы для разведки писать в системную временную папку, не в репозиторий (файлы `*_preview*.json` в `.gitignore`).

### 4.3. Технические особенности проекта

- **Leaflet и SSR.** `next/dynamic(..., { ssr: false })` можно вызывать только внутри Client Component (`'use client'`), не в Server Component. Юнит-тестами Leaflet не проверяется (ненадёжен в jsdom): вся логика в чистых функциях с тестами, сам рендер проверяется визуально на dev-странице.
- **Фикстуры в тестах** читаются через `fs` из `tests/fixtures/real/`. Тесты не должны зависеть от конкретных чисел живых статей.
- **Доступность в тестах.** Testing Library определяет имя кнопки по вложенному `alt`, поэтому у кнопок с картинками нужен явный `aria-label`.
- **Windows / PowerShell 5.1:** файлы записывать в UTF-8 без BOM (`pytest.ini` чувствителен к BOM, не использовать `Out-File -Encoding utf8`); `Get-Content` читать с `-Encoding utf8`. Backend запускается из `backend` с `.\venv\Scripts\Activate.ps1`. В `WikipediaClient` обязателен информативный User-Agent и `trust_env=False` (остаточный системный прокси VPN ломает httpx).
- **Запрещено без согласования:** `npm audit fix --force` (3 известные уязвимости отложены до Phase 10), обновление Next.js и других основных зависимостей, любые новые зависимости, кроме одобренных.

### 4.4. Что решает владелец (остановиться и спросить)

Claude Code готовит предложение и ждёт ответа владельца по пунктам:
- выбор библиотеки графиков и вид диаграммы (этап 6);
- визуальный вид `TimelineWidget` (этап 4);
- любое изменение контракта данных (Pydantic и TypeScript вместе), включая форму `Infobox`, если текущая не подходит;
- любые новые зависимости;
- изменение структуры `Table` (этап 7).

Как формулировать вопрос: одна страница простым языком, 2–3 варианта, что каждый даёт и чем грозит, своя рекомендация с причиной. Без ответа владельца на этих пунктах не продолжать, переходить к независимым этапам.

### Этап 1. Воспроизводимые фикстуры (P1, основа для остальных)

**Задача:** выгрузка фикстур по фиксированной ревизии статьи, чтобы повторный запуск не менял данные.
- MediaWiki `action=parse` принимает `oldid`; `RawArticle.revision_id` уже есть. Расширить `WikipediaClient` минимально (например, необязательный параметр ревизии), без выхода за четыре файла модуля.
- Манифест `frontend/tests/fixtures/real/manifest.json`: URL статьи, номер ревизии, имя файла. `export_fixtures` читает манифест; обновление ревизий только явным ключом (например, `--update`).
- Записать в манифест текущие ревизии трёх существующих статей. Добавить для проверки дат до нашей эры и разных вёрсток инфобокса: `Julius Caesar` (en) и `Сократ` (ru).
- Тесты клиента и разбора манифеста офлайн (мок httpx).
- Приёмка: двукратный запуск `export_fixtures` подряд не даёт изменений в `git diff`; все проверки зелёные; в отчёте перечислено, что изменилось в трёх старых фикстурах после перехода на зафиксированные ревизии.

### Этап 2. Исправления extractor'ов по итогам визуальной проверки (P1)

Для каждого пункта: разведка → красный тест → исправление → перевыгрузка фикстур → все проверки → коммит.

**2.1. Заголовки навигационных блоков в `sections`** (наблюдение 1). Запустить `python -m scripts.inspect_headings` (скрипт из репозитория, качает France), убедиться, что лишние заголовки лежат внутри `navbox`/`sidebar`/`role=navigation`. Исключить такие заголовки из разделов статьи. Проверить на en и ru. Сравнить списки разделов до и после: настоящие разделы не должны пропасть.

**2.2. Маркеры сносок в тексте ячеек** (наблюдение 2). Исключить из текста ячеек таблиц (`<sup class="reference">`), включая строку шапки. В `section_extractor.py` такая логика для заголовков уже есть (`_is_service_text`): предпочтительно вынести общую утилиту, чем дублировать, но без крупного рефакторинга. Проверить другие места, где извлекается текст: подписи изображений, `caption` таблиц.

**2.3. Код в ячейках разбит пробелами** (наблюдение 3). Сначала разведка реальной разметки (вероятно, подсветка синтаксиса вложенными `<span>` внутри `<code>` или `div.mw-highlight`). Цель: внутри одного элемента кода текст не разрывается, между отдельными элементами пробел сохраняется. Стратегию предложить по итогам разведки, кратко описать в отчёте.

### Этап 4. TimelineWidget (P1)

Данные: `events` (`id`, `date`, `date_precision`, `title`, `description`, `source`, `confidence`). Формат `date`: ISO `YYYY-MM-DD` для дня; для дат до нашей эры только год в виде `-000N` (упрощённая нумерация, без смещения на единицу, ТЗ §16.2). Точность: реально встречаются `day` и `year`. Источники: `infobox` (confidence 1.0) и `article_text` (confidence 0.6; в `title` лежит заголовок раздела, где найдена дата, — проверить на фикстурах).

Порядок работы:
1. Разведка: изучить `events` во всех фикстурах, включая Caesar и Сократ (даты до н. э.).
2. Предложение вида виджета (согласовать с владельцем, раздел 4.4). Исходное предложение: вертикальный список по возрастанию даты; дата показывается по-человечески с учётом точности и языка статьи («44 до н. э.», «14 March 1879»); отметка источника и уверенности.
3. Чистая логика в `lib/widgets/` (сортировка с отрицательными годами и смешанной точностью, форматирование дат) с тестами: одинаковые даты, `unknown` точность, некорректные строки (не падать).
4. Компонент, обёртка `Widget` (`timeline-widget`), `supports` (порог решить и обосновать), регистрация в `setup.ts` одной строкой, тесты по образцу остальных виджетов, добавить статьи в `/dev/widgets`.
