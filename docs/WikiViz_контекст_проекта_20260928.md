## 1. Что такое WikiViz

Веб-сервис, преобразующий статьи Wikipedia в интерактивное визуальное представление. URL статьи → MediaWiki API → извлечение структурированных элементов → единая внутренняя модель → подбор виджетов → страница результата с уникальным URL.

Тип проекта: учебный/исследовательский. Один разработчик (доктор философии, преподаёт в вузе, не программист по основной профессии, работает с NLP-терминологией). Спецификация: ТЗ v3.1 и Roadmap v3.1 (4 уровня: Foundation → Wikipedia MVP → Intelligent WikiViz → Universal Text Analysis Platform).

**Важное изменение процесса (с 28.09.2026):** оставшаяся часть Phase 6 передана агенту **Claude Code** — он пишет код, тестирует, коммитит в облачных сессиях (claude.ai/code). Claude в обычном чате теперь выполняет другую роль: пишет ТЗ для агента, помогает с настройкой, разбирает его отчёты, **независимо перепроверяет результат на компьютере владельца перед слиянием в `main`**. Точка передачи размечена тегом `before-claude-code` в git; спецификация лежит в репозитории — `docs/PHASE6_TZ.md`.

## 2. Архитектурные принципы

```
Extraction ≠ Transformation ≠ Visualization
Wikipedia → Extractor → Normalized Data → Transformer/Selector → Widget
```

Ключевые правила Roadmap: Rule 3 (Wikipedia HTML не контракт), Rule 4 (не создавать модель под виджет), Rule 5 (новые данные — сначала в Normalized Data Model), Rule 6 (виджеты подключаются через `WidgetRegistry` одной строкой — подтверждено уже пять раз: table, gallery, map, section-navigator, **timeline**).

## 4. Нормализованная модель (контракт backend ↔ frontend)

`NormalizedArticleModel`: `article`, `sections`, `infobox`, `tables`, `locations`, `events`, `numbers`, `people`, `organizations`, `works`, `relations`, `images`, `links`, `metadata`.

Статус заполнения: реальные данные — `article`, `sections`, `tables`, `locations`, `images`, `events`, `numbers`. Пустые заглушки — `infobox`, `people`, `organizations`, `works`, `relations`, `links`, `metadata`.

**Открытые вопросы по контракту (ждут решения владельца, см. §7):**

- `Infobox`: нужно ли поле `group` для группировки полей (например, France: три поля `Total` — площадь, ВВП по ППС, номинальный ВВП — без группы неотличимы).
- `Table`: нужно ли необязательное поле `notes` для строк вида «Источник: …», которые сейчас либо портят данные, либо теряются при исправлении шапки.

## 5. Backend

`app/wikipedia/`: 4 файла, без изменений архитектуры. `fetch_article` теперь принимает необязательный номер ревизии (для воспроизводимых фикстур).

`app/extractors/`: `section_extractor`, `section_normalizer`, `table_extractor`, `coordinate_extractor`, `image_extractor`, `date_extractor`, `text_date_extractor`, `number_extractor`, `article_normalizer`, и новый — **`text_utils.py`** (общая проверка «это сноска / служебный элемент», переиспользуется в `table_extractor` и `image_extractor`).

**Исправления за последние две сессии:**

- Скрытые sort-key spans (`display:none`) в ячейках таблиц — не попадают в текст.
- Маркеры сносок (`<sup class="reference">`) — исключены из ячеек таблиц (включая шапку), `caption` таблиц, подписей изображений.
- Код в ячейках с подсветкой синтаксиса — текст внутри одного фрагмента больше не разбивается пробелами (`bytearray(b'Some ASCII')`, а не `bytearray ( b 'Some ASCII' )`).
- `TextDateExtractor`: даты до н. э. больше не теряют маркер эпохи (было: `100 BC` → `0100-...`, стало: `-0100`, по ТЗ §16.2). Исключение служебных разделов (`References`, `External links` и т. п.) теперь распространяется на **все их вложенные подразделы**, не только на разделы с самим служебным названием.

**Известные ограничения (осознанные, не баги):**

- Текст ошибок Scribunto/Lua-шаблонов в таблицах не фильтруется.
- `colspan`/`rowspan` не обрабатываются (ТЗ §12.4) — практическое следствие: у таблицы населения Токио заголовок и подзаголовок колонок попадают в данные (кандидат на этап 7, ждёт решения по полю `notes`).
- **Новое, не исправлено:** таблицы-навигация Wikipedia (succession box, например «Preceded by / Succeeded by» у Цезаря) извлекаются как обычные таблицы с данными — `table_extractor` исключает по классу только `infobox` и `navbox`, а такие блоки, видимо, размечены как `wikitable`.
- `Introduction` (название вступления статьи для дат из текста) жёстко на английском, даже в русских статьях.
- Инфобокс Цезаря: `Pontifex maximus 64–44 BC` — extractor берёт год конца периода как отдельную дату, начало периода теряется.

Тесты: **166** (было 127 в начале сессии 28.09).

**Фикстуры теперь воспроизводимы.** `frontend/tests/fixtures/real/manifest.json`: пять статей с закреплёнными номерами ревизий — Python, France, Токио, **Julius Caesar (en, новая)**, **Сократ (ru, новая)**. Две новые добавлены ради покрытия дат до н. э. и другой вёрстки инфобокса. `python -m scripts.export_fixtures` качает только закреплённые ревизии; `--update` берёт свежие и обновляет манифест. Подтверждено: два запуска подряд не меняют `git diff`. **Ограничение:** закреплённая ревизия фиксирует текст статьи, но не общие шаблоны Wikipedia (навигация, вёрстка инфобокса) — они всегда актуальные, поэтому раз в несколько месяцев возможны мелкие расхождения при повторной выгрузке.

## 6. Frontend: Phase 6 — виджеты

### 6.1. Готово и зарегистрировано (пять из семи)

**`TableWidget`, `GalleryWidget`, `MapWidget`, `SectionNavigator`** — без изменений с прошлой сессии (см. предыдущую версию контекст-документа для деталей реализации).

**`TimelineWidget` (новый).** `lib/widgets/timeline.ts` (чистая логика: сортировка с отрицательными годами и смешанной точностью, форматирование дат по языку статьи и эре, 18 тестов) + `components/widgets/TimelineWidgetView.tsx` + `lib/widgets/timelineWidget.tsx`.

- Вид: вертикальный список по возрастанию даты (вариант «А» из трёх предложенных, выбран владельцем как самый простой при текущем отсутствии стилей).
- Порог показа: 2 события и больше.
- Строка: дата на языке статьи с учётом эры (`15 March 44`, `44 BC`, `14 марта 1879`, `469 до н. э.`) + источник и уверенность (`инфобокс, 100%` / `текст статьи, 60%`).
- Некорректная дата не роняет виджет — показывается как есть в конце списка.
- `supports = data.events.length >= 2`.

### 6.2. Осталось в Phase 6 — решения владельца нужны перед продолжением

**`InfoBoxWidget`** (этап 5 ТЗ). Заблокирован вопросом о форме контракта `Infobox`. Варианты (рекомендация Claude Code — Б):

- А — группа прямо в названии поля («Area — Total»), без изменения контракта.
- **Б (рекомендовано)** — необязательное поле `group` в `Infobox` (Pydantic + TypeScript синхронно), не ломает существующее.
- В — список групп с полями внутри вместо плоского словаря, меняет контракт целиком.

**`StatisticsChart`** (этап 6 ТЗ). Разведка: из пяти фикстур для диаграммы годится только одна группа — религии France (10 значений, `%`, данные иерархические, сумма 148% → только столбики, не круг). Варианты по реализации (рекомендация — А):

- **А (рекомендовано)** — без библиотеки, HTML/SVG вручную (~60 строк), работает в SSR и Jest.
- Б — Recharts (React-типы, готовые оси, ~100 КБ, клиентский компонент).
- В — Chart.js + react-chartjs-2 (canvas, не тестируется в jsdom).

**Шапка таблицы населения Токио** (этап 7 ТЗ, связан с известным ограничением `colspan`/`rowspan`). Варианты (рекомендация — Б):

- А — эвристика без изменения контракта, строка «Источник: …» отбрасывается.
- **Б (рекомендовано)** — то же плюс необязательное поле `notes` в `Table`, чтобы не терять указание источника данных.

## 9. Инструменты окружения

Всё из предыдущей версии документа (VPN-прокси, Docker, PowerShell-специфика) остаётся в силе. Дополнительно:

- **Claude Code CLI заблокирован в регионе владельца** (ошибка `403` при обращении к api.anthropic.com) — используются облачные сессии через claude.ai/code вместо локального `claude`.

Принцип: обход, нужный для одной среды, не должен просачиваться в код и ломать другую среду.
- Git: ветка работы агента — `claude/peaceful-clarke-dg7efr`, слита в `main` 28.09.2026 (`git merge --no-ff origin/<ветка>` — обязательно с `origin/`, иначе Git не найдёт ветку локально).
- **Правило перепроверки:** после каждой сессии агента владелец самостоятельно прогоняет `pytest`, `npx tsc --noEmit`, `npm test`, `npm run build` на своей машине и сверяет числа с отчётом агента, прежде чем `git push`. Отчётам агента доверяем, но проверяем.

## 10. Стиль работы с разработчиком

Всё из предыдущей версии документа остаётся в силе. Дополнительно, специфично для работы с Claude Code:

- ТЗ для агента пишется как отдельный файл в `docs/` репозитория, с явным разделением на этапы, критериями приёмки и разделом «что решает владелец» (архитектурные развилки, требующие явного ответа, а не решаемые агентом самостоятельно).
- Владелец отвечает агенту короткими решениями (вариант А/Б/В с обоснованием при необходимости), а не пишет код сам.
- Агент присылает отчёты по тому же принципу, что и раньше был у Claude в чате: что сделано и зачем, числа тестов до/после, что посмотреть глазами и по какому адресу, открытые вопросы, список коммитов.
- Слияние ветки агента в `main` и вся перепроверка — обязанность владельца (при поддержке Claude в чате), не самого агента.
