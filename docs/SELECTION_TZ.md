## 1. Цель и принцип

**Цель:** с любой статьи Wikipedia в визуализацию попадают только надёжные данные; лишнее отсекается правилами.

**Принцип:** лучше не показать, чем показать мусор. Пропущенную дату пользователь не заметит, а мусорная подрывает доверие ко всей странице.

**Что считается «надёжным» значением:**
- оно действительно относится к теме статьи (дата события, а не дата публикации источника);
- оно правильно разобрано (число с понятной единицей, таблица с выровненными колонками);
- оно не повторяет уже показанное.

**Границы.** Отбор не исправляет разбор (это задача extractors) и не решает, как показывать (это задача виджетов). Он только говорит «показывать / не показывать» и почему.

## 2. Место в архитектуре

```
Wikipedia → Extractors → NormalizedArticleModel → ОТБОР → выбор виджетов → виджеты
              (всё найденное, честно)            (правила, причины)   (есть ли у виджета отобранные данные)
```

- Extractors не цензурируют: они отвечают за точность разбора, а не за полезность. Так ошибки разбора остаются видны.
- Отбор — отдельный слой, это и есть «Transformation» из принципа `Extraction ≠ Transformation ≠ Visualization`.
- Виджеты получают отобранные данные и сами больше ничего не фильтруют. Сейчас StatisticsChart и Timeline содержат свои пороги — они переезжают в отбор.

### В1. Где работает отбор

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. Backend, после нормализации** (рекомендация) | отобранный результат сразу идёт в API и Redis (Phase 8–9); правила на Python рядом с данными корпуса и тестами; frontend получает готовое | dev-страницам нужен отдельный путь, чтобы видеть отброшенное (см. В3) |
| Б. Frontend, перед выбором виджетов | правила рядом с виджетами | логика данных в React — нарушение принципа разделения; при каждом показе пересчёт |

**Рекомендация: А. Решение владельца (18.10): А.**

## 3. Откуда пришло значение (происхождение)

Главный признак шума, найденный корпусом, — **место в статье**:

| Статья | Даты из пунктов списков | Даты из абзацев |
|---|---|---|
| Гагарин | 423 | 31 |
| Новосибирск | 560 | 58 |
| Казахстан | 681 | 50 |

Сейчас extractors эту информацию выбрасывают: у события есть только заголовок раздела. Без неё отбор вынужден угадывать.

### В2. Как дать отбору происхождение значений

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. Extractors записывают происхождение** (рекомендация) | честный признак «список/абзац/таблица/инфобокс/подпись» для любого правила; это упрощённый Provenance из ТЗ §21 | изменение контракта (Pydantic + TypeScript); перевыгрузка корпуса и фикстур |
| Б. Отбор сам перечитывает HTML | контракт не меняется | отбор завязан на разметку Wikipedia (нарушение Rule 3), двойной разбор HTML при и так медленной нормализации |
| В. Extractors сами выбрасывают «подозрительное» (например, даты из списков) | просто | разбор и отбор смешиваются; выброшенное не видно и не оспорить |

**Рекомендация: А. Решение владельца (18.10): А — происхождение записываем.** Предлагаемая форма (минимальная, только то, чем пользуются правила ниже):

```json
"context": {
  "block": "paragraph",            // infobox | paragraph | list_item | table | caption | heading
  "section_path": ["History", "Early life"],
  "service_section": false         // внутри служебного раздела (литература, ссылки…) или его подраздела
}
```

- Поле `context` необязательное, добавляется к `Event`, `NumericValue`, `Image` (и в будущем к сущностям).
- `Table` и `InfoboxField` его не получают: их происхождение и так известно по типу.
- Даты из служебных разделов extractor уже сейчас не извлекает; `service_section` нужен для изображений и на будущее.

## 4. Что отдаёт отбор

### В3. Форма результата

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. Отобранная модель + список отброшенного с причинами** (рекомендация) | виджеты получают обычный `NormalizedArticleModel`, только отфильтрованный; dev-страница и проверка точности видят, что и почему отброшено | список отброшенного нужно хранить (в API — только для dev-режима) |
| Б. Пометка у каждого значения (`selected: true/false`, `reason`) | всё в одном месте | контракт меняется у каждой модели; каждый виджет должен помнить про пометку |
| В. Только журнал (лог) | контракт не меняется | отброшенное не видно на dev-странице, точность не измерить |

**Рекомендация: А. Решение владельца (18.10): А.** Набросок:

```json
{
  "selected": { ...NormalizedArticleModel... },
  "rejected": [
    { "kind": "event", "ref": "text-event-17", "preview": "2015-05-21 «Статьи»",
      "rule": "EV-LIST", "reason": "дата из пункта списка" }
  ]
}
```

Правило всегда называется кодом (`EV-LIST`) и человеческой фразой — чтобы на dev-странице было понятно и можно было оспорить.

## 5. Каталог правил

Обозначения: **код** — короткое имя правила; **эффект** — оценка на корпусе; **статус** — «предлагается» или «под вопросом» (нужна проверка или решение).

Правила применяются по порядку внутри типа данных; первое сработавшее даёт причину отбрасывания.

### 5.1. Даты (Timeline)

Сейчас: 1340 событий, из них 1298 из текста; 759 дат из текста не раньше 2000 года; 492 даты из разделов, где дат 10 и больше; 119 повторов одной даты в разных разделах.

| Код | Правило | Пример из корпуса | Эффект | Статус |
|---|---|---|---|---|
| EV-LIST | дата из пункта списка не показывается | Гагарин, «Почётные звания и награды» — 257 дат | основной отсев (нужно `context`, В2) | предлагается |
| EV-DENSE | раздел, давший N и больше дат из абзацев, считается перечнем и не показывается | Эйнштейн, «Scientific» — 32 | 492 даты при N = 10 (вместе со списками) | под вопросом: порог N, проверить, что не режет военные статьи (World War II) |
| EV-DUP | одна дата показывается один раз: инфобокс важнее текста, первый раздел важнее последующих | 119 повторов | −119 | предлагается |
| EV-FUTURE | дата позже даты ревизии статьи не показывается | — | мало, страховка | предлагается |
| EV-MIN | шкала показывается при 2 и больше событиях **после** отбора | сейчас 36 статей из 48 проходят до отбора | — | предлагается (переезд из виджета) |
| EV-MAX | на шкале не больше K событий; при избытке — приоритет инфобоксу, затем абзацам раннего раздела | — | — | под вопросом: K (20?) или вместо этого группировка (вариант Б вида шкалы) |

Чего **нет** в списке и почему: «дата позже 2000 года — подозрительна» — не правило: у ЧМ-2018 и Google такие даты осмысленны.

## 6. Как проверяется качество

### В4. Цель по точности

Точность = доля показанных значений, которые владелец признаёт верными.

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. 90% по каждому типу данных** (рекомендация) | строго, но достижимо для дат и чисел с правилами выше | на таблицах может потребовать дополнительных правил |
| Б. 95% | почти без мусора | много хорошего уйдёт под нож |
| В. 80% | быстро | мусор заметен глазу |

**Решение владельца (18.10): А.**

### В5. «Золотой набор» — защита от слишком жёсткого отбора

Для 10–15 статей корпуса владелец отмечает 3–5 фактов, которые **обязаны** остаться (дата рождения, площадь страны, главная таблица, ключевая иллюстрация). Правило принимается, если точность растёт и ни один золотой факт не пропадает.

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. Владелец размечает на dev-странице корпуса** (рекомендация) | разметка в одном месте, сохраняется в репозиторий (`backend/tests/corpus/golden.json`) | нужно сделать страницу (сессия 4) |
| Б. Claude Code предлагает набор, владелец утверждает списком | быстрее | риск подогнать набор под правила |

**Решение владельца (18.10): А.**

### В6. Кто и как размечает выборку для точности

| Вариант | Что даёт | Чем грозит |
|---|---|---|
| **А. Случайная выборка ~100 показанных значений по типам, разметка «верно / мусор» на dev-странице** (рекомендация) | честная оценка, повторяемая после каждого изменения правил | около часа работы владельца на одну разметку |
| Б. Владелец смотрит 10 статей целиком | естественно | точность не посчитать числом |

**Решение владельца (18.10): А.**

**Контрольная группа.** Шесть случайных статей корпуса (`random-*`) не используются для подбора порогов: на них правило проверяется последним. Если правило помогает выбранным статьям, но портит случайные — оно подогнано.

## 7. План реализации (сессия 4, после решений)

1. Если В2 = А: поле `context` в моделях (Pydantic + TypeScript синхронно), заполнение в extractors, перевыгрузка корпуса и фикстур.
2. Модуль отбора на backend (`app/selection/` или `app/transformers/` — уже существующая пустая папка): по правилу — чистая функция с тестом «шум отсекается / настоящее остаётся» на примерах из корпуса.
3. Форма результата по В3; `normalize → select` в одном месте (будущий API Phase 8 вызывает оба шага).
4. Переезд порогов из виджетов (`statistics.ts`, `timelineWidget.tsx`) в отбор; `supports` смотрит на отобранные данные.
5. Dev-страница корпуса: показано / отброшено с причинами; разметка «верно / мусор» и золотых фактов (В5, В6).
6. Замер точности до и после; проверка на контрольной группе; отчёт.

**Готово, когда:** цель по точности (В4) достигнута по каждому типу, золотые факты на месте, контрольная группа не хуже, все проверки зелёные.
