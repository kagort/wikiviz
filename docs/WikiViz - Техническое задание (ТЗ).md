# 1. Общая концепция

## 1.1. Назначение

**WikiViz** — веб-сервис для автоматического преобразования структурированного и неструктурированного текста в интерактивное визуальное представление.

Основной сценарий MVP — анализ статей Wikipedia.

Архитектура системы при этом должна быть изначально построена таким образом, чтобы в последующих версиях поддерживать анализ произвольных пользовательских текстов, в частности TXT, без изменения основного NLP-движка и системы визуализации.

Пользователь может в перспективе передавать:

- URL статьи Wikipedia;
- сырой текст;
- TXT-файл;
- другие текстовые форматы.

Все источники после этапа загрузки должны преобразовываться в единую внутреннюю модель документа.

Основной принцип системы:

```text
Input
  ↓
Source Adapter
  ↓
Raw Data
  ↓
Extraction / Parsing
  ↓
Normalized Document Model
  ↓
NLP / Transformation
  ↓
Widget Selection
  ↓
Visualization
  ↓
Temporary Result
```

Wikipedia является одним из источников данных, а не частью NLP-ядра.

# 2. Основные цели проекта

## 2.1. Цели MVP

MVP должен позволять:

1. принять URL статьи Wikipedia;
2. проверить корректность URL;
3. получить статью через MediaWiki API;
4. извлечь основные структурированные элементы;
5. привести данные к единой внутренней JSON-модели;
6. определить, какие визуализации применимы;
7. построить страницу результата;
8. предоставить уникальный URL результата;
9. хранить результат ограниченное время;
10. корректно обрабатывать ошибки;
11. работать на мобильных устройствах;
12. запускаться локально через Docker.

## 2.2. Архитектурные цели последующих версий

Архитектура MVP должна позволять без изменения NLP-движка добавлять новые источники текста:

```text
Wikipedia
TXT
Plain text input
Markdown
HTML
PDF
DOCX
API
...
```

В частности, последующая версия должна поддерживать:

```text
User TXT
   ↓
Text Adapter
   ↓
Normalized Document
   ↓
NLP Engine
   ↓
Entity / linguistic / semantic analysis
   ↓
Visualization
```

Полноценная реализация пользовательского TXT-анализа **не входит в MVP**, но возможность её реализации является архитектурным требованием.

---

# 3. Принцип расширяемости

Архитектура WikiViz должна следовать принципу:

> **Source ≠ Extraction ≠ Transformation ≠ NLP ≠ Visualization.**

То есть:

```text
Source
   ↓
Source Adapter
   ↓
Extractor
   ↓
Normalized Document
   ↓
NLP / Transformer
   ↓
Widget Selector
   ↓
Widget
```

Wikipedia-specific код не должен попадать в NLP-движок.

Например:

```text
WikipediaAdapter
TXTAdapter
MarkdownAdapter
```

должны формировать совместимую внутреннюю модель:

```text
NormalizedDocument
```

После этого NLP-движок работает одинаково независимо от источника.

# 6. MediaWiki API — Wikipedia Source Adapter

Получение данных из Wikipedia должно выполняться исключительно через официальный MediaWiki API. Прямой scraping Wikipedia как основной механизм получения статьи не используется.

В терминологии актуальной архитектуры (§10, Source Adapter Layer) модуль, описанный в этом разделе, **является реализацией `WikipediaAdapter`** — он отвечает только за получение сырых данных и их первичное представление, не выполняет извлечение (extraction), нормализацию или NLP-анализ.

## 6.1. Основные категории данных, получаемых через API

```text
Article metadata
Article HTML
Sections
Links
Coordinates
Images
Revisions / metadata
```

## 6.2. Структура модуля **[РЕАЛИЗОВАНО]**

API-клиент вынесен в отдельный модуль, строго ограниченный следующими файлами (расширение сверх этого списка не допускается — извлечение и нормализация физически выносятся в `app/extractors/`, см. §11):

```text
backend/
└── app/
    └── wikipedia/
        ├── client.py       — parse_wikipedia_url() + класс WikipediaClient
        ├── models.py       — RawArticle
        ├── errors.py       — иерархия исключений
        └── endpoints.py    — (зарезервирован для построения query-параметров;
                               на момент реализации Phase 2 построение запроса
                               остаётся внутри client.py)
```

## 6.3. `RawArticle` — промежуточная модель **[РЕАЛИЗОВАНО]**

```python
class RawArticle(BaseModel):
    page_id: int
    title: str
    language: str
    url: str
    html: str
    revision_id: Optional[int] = None
```

`RawArticle` — сырое представление, полученное непосредственно от MediaWiki API. Не смешивается с `NormalizedArticleModel` (§7) и не покидает границу Source Adapter Layer как часть публичного API-контракта.

## 6.4. Разбор URL **[РЕАЛИЗОВАНО]**

`parse_wikipedia_url(url) -> tuple[language, title]` — чистая функция без сетевого взаимодействия. Обязанности:

- валидация, что URL абсолютный и указывает на домен вида `{lang}.wikipedia.org` или `{lang}.m.wikipedia.org` (мобильная версия)
- извлечение кода языка и заголовка статьи
- автоматическое отбрасывание якоря (`#Section`)
- URL-декодирование заголовка (поддержка не-ASCII заголовков — кириллица и др.)

При ошибке бросает `InvalidURLError` (URL синтаксически некорректен или не указывает на статью) либо `UnsupportedDomainError` (домен не относится к Wikipedia).

## 6.5. HTTP-клиент **[РЕАЛИЗОВАНО]**

`WikipediaClient.fetch_article(url) -> RawArticle` — обращается к `https://{language}.wikipedia.org/w/api.php` с параметрами:

```text
action=parse
page=<title>
prop=text|revid
redirects=1
format=json
formatversion=2
```

Обязательные технические требования, подтверждённые практикой:

- **Информативный User-Agent обязателен** — MediaWiki API возвращает `403` без него.
- Редиректы Wikipedia обрабатываются на уровне самого API (`redirects=1`), отдельная логика в клиенте не требуется.
- Клиент должен быть устойчив к системным proxy-настройкам окружения, которые не относятся к самому запросу (например, остаточный VPN-прокси) — рекомендуется явный контроль доверия к переменным окружения на уровне HTTP-клиента.

Ошибки:

- Статья не существует (`missingtitle`, `invalidtitle` в ответе API) → `ArticleNotFoundError`
- Сетевая ошибка, таймаут, HTTP-ошибка, невалидный/неожиданный формат ответа → `WikipediaAPIError`

# 7. Внутренняя модель данных

Это один из самых важных элементов проекта.

Backend не должен передавать frontend «сырой Wikipedia HTML» как основную модель.

Необходимо создать **Normalized Document Model**, частью которого является специализированная модель статьи Wikipedia.

Рекомендуемая архитектура:

```text
NormalizedDocument
│
├── metadata
├── structure
├── content
├── entities
├── relations
├── linguistic_data
└── provenance
```

Wikipedia может дополнительно предоставлять:

```text
article
infobox
tables
locations
events
images
links
sections
```

Таким образом:

```text
Wikipedia Article
       ↓
NormalizedDocument
       ↓
NLP
```

и:

```text
TXT
       ↓
NormalizedDocument
       ↓
NLP
```

используют одно и то же NLP-ядро.

**Практическое состояние на момент написания:** реализованная на сегодня модель (`NormalizedArticleModel`, Phase 1) — это специализированное Wikipedia-представление в духе §7, состоящее из `article`, `sections`, `infobox`, `tables`, `locations`, `events`, `numbers`, `people`, `organizations`, `works`, `relations` (заглушка), `images`, `links`, `metadata`. Формальное разделение на универсальный внешний слой `NormalizedDocument` (§8) и вложенное Wikipedia-специфичное представление ещё не выполнено технически — это отложено до Phase 15 актуального Roadmap («Universal Document Model»), когда появится более одного источника данных и разделение станет предметно необходимым, а не преждевременной абстракцией.

*Состояние на 2026-10-08 (после Phase 6):* реальными данными заполняются `article`, `sections`, `infobox`, `tables`, `locations`, `images`, `events`, `numbers`; заглушки — `people`, `organizations`, `works`, `relations`, `links`, `metadata`. Изменения контракта Phase 6 (одобрены владельцем, синхронно в Pydantic и TypeScript): `InfoboxField.group` — подзаголовок группы полей инфобокса (§11); `Table.notes` — строки таблицы во всю ширину, не являющиеся данными (§12.2).

# 8. Universal Document Model

В системе должна существовать универсальная абстракция:

```text
Document
```

Минимальная концептуальная модель:

```json
{
  "id": "document-001",
  "source": {
    "type": "wikipedia",
    "identifier": "123"
  },

  "metadata": {},

  "structure": {
    "sections": []
  },

  "content": {
    "paragraphs": [],
    "lists": [],
    "tables": [],
    "images": []
  },

  "entities": [],
  "relations": [],
  "linguistic_data": {},

  "provenance": {}
}
```

Для Wikipedia `source.type` может быть:

```text
wikipedia
```

Для пользовательского текста:

```text
txt
```

Для других источников:

```text
markdown
html
pdf
docx
api
```

Наличие универсальной модели является обязательным архитектурным требованием.

# 9. Entity model

В системе с самого начала должна существовать базовая абстракция:

```text
Entity
```

Минимальная модель:

```json
{
  "id": "entity-001",
  "type": "person",
  "label": "Albert Einstein",
  "description": null,
  "source": "infobox",
  "confidence": 1.0
}
```

Для NLP-извлечения источник может иметь значение:

```text
nlp
```

Например:

```json
{
  "id": "entity-002",
  "type": "person",
  "label": "Albert Einstein",
  "source": "nlp",
  "confidence": 0.94
}
```

Таким образом одна и та же модель Entity должна использоваться как для Wikipedia extraction, так и для последующего NLP-анализа произвольных текстов.

# 10. Source Adapter Layer

Для отделения источника данных от последующих этапов необходимо предусмотреть слой адаптеров.

Концептуально:

```text
sources/
├── wikipedia/
│   └── adapter.py
├── txt/
│   └── adapter.py
├── markdown/
│   └── adapter.py
└── html/
    └── adapter.py
```

Адаптер отвечает только за получение исходного содержимого и его первичное представление.

Он не должен выполнять:

- NER;
- relation extraction;
- выбор виджетов;
- визуализацию.

Пример:

```text
WikipediaAdapter
        ↓
RawArticle

TxtAdapter
        ↓
RawText
```

После этого данные передаются в соответствующий parser / normalizer.

**Практическое состояние на момент написания:** единственный реализованный адаптер — Wikipedia (§6); физически он размещён в `app/wikipedia/`, а не в `app/sources/wikipedia/`, как показано в концептуальной схеме этого раздела — переезд в формальный `sources/`-слой целесообразен при добавлении второго адаптера (Phase 16 Roadmap, `TxtAdapter`), не раньше, чтобы не создавать структуру ради одного элемента.

# 11. Extraction layer

Extraction должен быть разбит на независимые модули.

Для Wikipedia:

```text
extractors/
├── infobox_extractor.py
├── table_extractor.py
├── coordinate_extractor.py
├── image_extractor.py
├── section_extractor.py
├── date_extractor.py
└── number_extractor.py
```

В дальнейшем:

```text
├── person_extractor.py
├── location_extractor.py
├── organization_extractor.py
├── event_extractor.py
├── work_extractor.py
├── concept_extractor.py
└── relation_extractor.py
```

Для произвольного текста должен существовать отдельный NLP-oriented extraction layer:

```text
nlp/
├── tokenizer.py
├── morphology.py
├── syntax.py
├── entities.py
├── relations.py
└── semantics.py
```

Wikipedia extraction и NLP extraction не должны смешиваться.

**Практическое состояние на момент написания [РЕАЛИЗОВАНО частично]:** из перечисленного списка реализованы `table_extractor.py`, `coordinate_extractor.py`, `image_extractor.py`, `section_extractor.py`, `date_extractor.py` (с дополнительным `text_date_extractor.py`, не предусмотренным исходным списком файлов, но необходимым по факту реализации — см. §16.1.2). `infobox_extractor.py` как отдельный файл не создавался: извлечение полей infobox выполняется внутри `date_extractor.py` напрямую, поскольку на данный момент единственное востребованное применение infobox — извлечение дат; выделение отдельного infobox-extractor'а целесообразно, если появится необходимость извлекать из infobox иные типы данных помимо дат. `number_extractor.py` — последний нереализованный extractor текущей фазы (Phase 4 Roadmap), спецификация — §17.

*Состояние на 2026-10-08:* реализованы все extractors списка, кроме будущих entity-extractors. `number_extractor.py` реализован в Phase 4. **`infobox_extractor.py` создан в Phase 6**, когда инфобокс понадобился целиком (`InfoBoxWidget`); `date_extractor.py` и `number_extractor.py` по-прежнему читают инфобокс сами и не переписывались. Правила `infobox_extractor`: первый `table.infobox`; строка = первые две ячейки; группы (`group`) — из строк-заголовков `infobox-header`/`infobox-subheader` и строк с «•», привязанных к предыдущей строке без «•»; из текста убираются сноски, скрытые элементы (`display:none`) и `.noprint` (например, «35 years ago», пересчитываемое при каждом запросе); списки и `<br>` в значениях — через запятую, в подписях `<br>` — пробел; строки с изображениями, заголовки над таблицей и подписи внизу — не поля; ключи уникальны и не состоят из одних цифр. Известное ограничение: особая вёрстка с двумя параллельными колонками (World War II: стороны конфликта) разбирается неверно. Общая утилита `text_utils.py` (признак сноски) используется несколькими extractors.

# 12. Таблицы **[РЕАЛИЗОВАНО]**

Система должна обнаруживать HTML-таблицы Wikipedia, содержащие информационные данные — в противоположность структурным таблицам иного назначения (infobox, навигационные блоки).

## 12.1. Источник в HTML

Извлекаются только `<table class="wikitable">`. MediaWiki размечает этим классом именно информационные таблицы с данными; `infobox` (§6 модели Wikipedia-специфичного infobox) и `navbox` (навигационные шаблоны) — тоже `<table>`, но не являются целью этого extractor'а и должны быть явно исключены.

## 12.2. Модель `Table`

```json
{
  "id": "table-1",
  "title": "Population",
  "columns": ["Year", "Population"],
  "rows": [["2000", "100000"], ["2010", "120000"]],
  "source": "table"
}
```

- `title` — текст из `<caption>`, если присутствует, иначе `null`.
- `columns` — текст ячеек первой строки таблицы (`<th>` или `<td>`).
- `rows` — текст ячеек последующих строк.
- Текст ячейки, содержащей несколько вложенных inline-элементов (например, `<code>A</code><code>B</code>`), должен склеиваться через пробел (`" ".join(stripped_strings)`), а не впритык — иначе значения теряют читаемость (обнаружено на реальных данных: `True`/`False` в ячейке типов Python склеивались в `TrueFalse` при наивном извлечении текста).
- Пустая ячейка → `""`, не `null`.

*Уточнения по факту реализации (2026-10-08):*
- Маркеры сносок (`<sup class="reference">`) исключаются из ячеек, шапки и `caption`.
- Текст внутри одного `<code>` (подсветка синтаксиса дробит выражение на `<span>`) склеивается как есть, без пробелов; между разными элементами пробел сохраняется.
- `columns` — шапка таблицы: первая строка, либо несколько строк из одних `<th>`, если в предыдущей строке шапки есть ячейка с `colspan` (названия собираются сверху вниз через « — »: «Возраст — до 15»). Строка `<td>` во всю ширину над такой шапкой становится `title` (или попадает в `notes`, если есть `caption`).
- `notes` (список строк, новое поле Phase 6) — строки во всю ширину, не являющиеся данными: пояснение над шапкой при наличии `caption` и примечания под данными («Источник: …»).

## 12.3. Обязательные пользовательские возможности (реализуются на уровне widget, Phase 6.3)

Таблица должна быть доступна для: просмотра, сортировки, поиска, фильтрации, пагинации.

## 12.4. Известные ограничения MVP

Объединённые ячейки (`colspan`/`rowspan`) не обрабатываются — строки могут не совпадать по количеству столбцов, если такие ячейки встречаются в реальной таблице.

*2026-10-08:* объединённые ячейки **шапки** обрабатываются (§12.2). В **строках данных** `rowspan` до сессии 2б не раскрывался: на корпусе из 48 статей у 31 таблицы из 122 (25%) больше трети строк не совпадали по длине с шапкой. **[РЕАЛИЗОВАНО 2026-10-08]:** строки данных раскладываются по сетке — значение ячейки с `rowspan` повторяется в покрытых строках, с `colspan` — в покрытых колонках; смещённых таблиц осталось 9 (таблицы вёрстки и таблицы с `<th>`-названием над шапкой из `<td>`, неотличимые от таблиц без шапки). Название таблицы склеивается с сохранением пробелов исходного HTML. Таблицы-навигация («Preceded by / Succeeded by») размечены как `wikitable` и извлекаются как таблицы с данными — вопрос для правил отбора.

# 13. Координаты **[РЕАЛИЗОВАНО]**

Система должна извлекать координаты из доступных структурированных источников HTML-разметки статьи.

## 13.1. Источник в HTML

Координаты, сгенерированные шаблоном `{{coord}}`, размечаются в **DMS-формате** (градусы/минуты/секунды, не десятичном): `<span class="latitude">27°59′18″N</span>` / `<span class="longitude">86°55′31″E</span>`. Секунды присутствуют не всегда (например, `57°18′N`).

## 13.2. Модель `Location`

```json
{
  "id": "location-1",
  "name": "Ulm",
  "latitude": 48.4011,
  "longitude": 9.9876,
  "description": null,
  "source": "coordinate",
  "confidence": 1.0
}
```

- **DMS → десятичные градусы:** обязательная конвертация на этапе извлечения (южная широта и западная долгота — со знаком минус).
- **Название точки:** предпочтительный источник — параметр `title` соседней ссылки на `geohack.toolforge.org` (присутствует у координат, встроенных в таблицы; отсутствует у единственной infobox-координаты статьи). При отсутствии — используется заголовок статьи как резервное значение.
- Параметр `params` той же geohack-ссылки **не является надёжным источником** для парсинга (формат непостоянен: то DMS, то десятичные градусы, с произвольными модификаторами `type:`/`scale:`/`region:`) — не должен использоваться как основной путь извлечения координат.

## 13.3. Множественные координаты

Статья может содержать несколько координат (например, список географических объектов в таблице — подтверждено на реальном примере статьи о группе вершин). Система должна извлекать все найденные координаты, а не только первую.

## 13.4. Дедупликация

Одна и та же координата может быть упомянута в HTML статьи более одного раза (например, и в infobox, и в тексте). Требуется удаление точных дублей (сравнение с округлением, чтобы избежать ложных различий из-за погрешности вычислений с плавающей точкой) при сохранении координат, которые лишь незначительно отличаются и представляют разные точки.

# 14. Изображения **[РЕАЛИЗОВАНО]**

## 14.1. Источник в HTML

Два типа контейнеров:

- **Иллюстрация в теле статьи:** `div.thumb` (за исключением содержащих `mw-kartographer-map` — сгенерированные карты положения, не фотографии), с `<img>` и подписью в `div.thumbcaption`.
- **Изображение infobox:** `td.infobox-image`, содержащее `<img>`; подпись (если есть) — в следующей строке той же таблицы, класс `infobox-caption`.

~~Реальная разметка MediaWiki не использует тег `<figure>`.~~ **Устарело (2026-10-08).** Проверка на корпусе показала, что Wikipedia перешла на новую разметку: обычная иллюстрация в тексте статьи — `<figure typeof="mw:File/Thumb">` с подписью в `<figcaption>`; блок `div.thumb` остался только внутри галерей (`div.gallerybox`), где подпись лежит в `.gallerytext`. До сессии 2б extractor эту разметку не поддерживал: основные иллюстрации статей не извлекались, а из галерей изображения приходили без подписей (на корпусе — 292 из 331 без подписи). **[РЕАЛИЗОВАНО 2026-10-08, сессия 2б]:** тело статьи — в порядке документа `<figure typeof="mw:File…">` с подписью в `<figcaption>`, `div.thumb` с подписью в `.thumbcaption` и картинки галерей с подписью в `.gallerytext`; пропускаются аудио и видео (нет `<img>`), карты `mw-kartographer-map`, картинки в таблицах (изображение инфобокса — отдельным путём), навигации и служебных блоках (`.navbox`, `.side-box`, `.noprint` и т. п.). На корпусе: 1310 изображений, 97% с подписью.

## 14.2. Модель `Image`

```json
{
  "url": "https://upload.wikimedia.org/.../1280px-Example.jpg",
  "thumbnail_url": "https://upload.wikimedia.org/.../330px-Example.jpg",
  "caption": "A simple caption",
  "alt": "An example",
  "source": "article_text"
}
```

- **Протокол-независимые URL** (`//upload.wikimedia.org/...`) нормализуются в `https://`.
- **`url`** формируется заменой размера в пути того же CDN-превью на более крупный (например, `/330px-` → `/1280px-`), без дополнительного сетевого запроса за оригиналом полного разрешения (осознанное упрощение MVP).
- **Caption** извлекается со склейкой через пробел при наличии вложенных ссылок (та же проблема и то же решение, что и для ячеек таблиц, §12.2) и с исключением текста служебной иконки «увеличить» (`div.magnify`), не несущей содержательного текста.
- **Дедупликация** — по имени файла (извлекается из `href` ссылки `class="mw-file-description"`, ведущей на `/wiki/File:...`), с резервным сравнением по URL превью, если имя файла определить не удалось.

## 14.3. Целевой сценарий использования

Изображения отображаются в `GalleryWidget` (Phase 6.4 Roadmap): `thumbnail_url` — превью в сетке, `url` — увеличенная версия (lightbox), `caption`/`alt` — подпись и атрибут доступности соответственно.

# 15. Sections (Разделы статьи) **[РЕАЛИЗОВАНО]**

## 15.1. Источник в HTML

Разделы определяются заголовками `h2`–`h6`. Реальная разметка MediaWiki оборачивает заголовок вспомогательным контейнером:

```html
<div class="mw-heading mw-heading2">
    <h2 id="History">History</h2>
    <span class="mw-editsection">[edit]</span>
</div>
<p>Содержимое раздела...</p>
```

Содержимое раздела является sibling-ом контейнера `div.mw-heading`, а не самого `<h2>` — при наличии такого контейнера именно он, а не заголовок, служит границей раздела. Должна поддерживаться и разметка без обёртки (`<h2>` напрямую).

Правило определения границ: раздел начинается с заголовка (или его обёртки) и продолжается до следующего заголовка любого уровня; контент до первого заголовка статьи не входит ни в один раздел на уровне структуры (обрабатывается отдельно, если требуется извлечение данных из вводного текста — см. §16.1.2).

## 15.2. Модель `Section`

```json
{
  "id": "section-3",
  "title": "Syntax and semantics",
  "level": 2,
  "children": [
    { "id": "section-4", "title": "Indentation", "level": 3, "children": [] }
  ]
}
```

- Дерево строится из плоского списка найденных заголовков через сопоставление по уровню вложенности (алгоритм на стеке: раздел с большим уровнем становится ребёнком ближайшего предшествующего раздела с меньшим уровнем).
- **`Section` не содержит HTML-содержимого раздела** — только структуру (заголовок, уровень, вложенность). Это осознанное архитектурное решение (соответствует §43, «не использовать Wikipedia HTML как внутренний API contract»): `SectionNavigator` (widget, для которого предназначена эта модель) использует только заголовки и дерево для построения оглавления, полный HTML раздела не требуется и излишне утяжелял бы контракт API и хранение результата в Redis.
- Внутреннее промежуточное представление с HTML-содержимым раздела (используется другими extractors для локализации данных внутри конкретного раздела статьи) существует отдельно, на уровне реализации `app/extractors/`, и не является частью публичного контракта.

# 16. Даты **[РЕАЛИЗОВАНО]**

## 16.1. Два независимых источника

### 16.1.1. Infobox (основной, высокая точность)

Современные даты в infobox почти всегда сопровождаются машиночитаемым ISO-представлением в скобках рядом с человекочитаемым текстом: `18 April 1955 (1955-04-18)`. Извлечение опирается на паттерн `(YYYY-MM-DD)` в тексте ячейки данных, а не на конкретный CSS-класс — наличие класса `bday` (микроформат hCard) непостоянно даже в пределах одной статьи (присутствует у даты рождения, отсутствует у даты смерти).

**Структурное расхождение между языковыми разделами Wikipedia:** строка infobox должна трактоваться как пара «заголовок, значение» через первые две ячейки строки (`<th>` или `<td>`, без привязки к конкретному тегу), поскольку вёрстка отличается между локалями:

- Английская Wikipedia: два `<td>` (`infobox-label` / `infobox-data`) — *2026-10-08: в актуальной разметке подпись обычно `<th class="infobox-label">`, значение `<td class="infobox-data">`; правило «первые две ячейки» покрывает оба варианта.*
- Русская Wikipedia: `<th>` + `<td>` (оба класса `plainlist`)

Даты извлекаются **исключительно** из `<table class="infobox">`. Обычные `wikitable` и, тем более, `navbox` (навигационные шаблоны, общие для многих статей одной категории) не должны рассматриваться как источник — подтверждено на практике: поиск без такого ограничения даёт систематические ложные срабатывания (строки общего навигационного шаблона с одинаковым, не относящимся к конкретной статье результатом на разных статьях одной тематической группы; строки обычных таблиц, где пара «подпись, значение» означает не событие, а, например, «автор оценки — предполагаемая им дата»).

*Дополнение (2026-10-08, сессия 2б):* если ISO-записи нет, берётся первая полная дата текста ячейки в форматах «7 September 1822», «July 4, 1776», «18 января 1871 года» (общий разбор с §16.1.2); у диапазона это начало («1 September 1939 – 2 September 1945» → 1939-09-01). Ограничение: если у начала диапазона нет года («22 February – 20 August 1969»), берётся конец. На корпусе события из инфобоксов: 24 → 42.

### 16.1.2. Обычный текст статьи (дополнительный, пониженная точность)

Не у всех типов статей есть чёткое поле даты в infobox (например, у международных организаций дата основания часто присутствует только в описательном тексте раздела истории). Для таких случаев дополнительно реализовано извлечение дат вида «день месяц год» из обычного текста статьи через словарь названий месяцев (английский и русский), без анализа смысла предложения (не NER, не relation extraction — механический паттерн-мэтчинг, попадающий в границы, допустимые для MVP согласно §4.3).

Дата привязывается к заголовку раздела, где была найдена (переиспользуется механизм из §15), либо к условному значению `"Introduction"` для текста до первого заголовка статьи. Поскольку привязка к заголовку раздела — не то же самое, что точная привязка к конкретному полю infobox, `confidence` для дат, извлечённых из текста, ниже (рекомендуемое значение — `0.6`), чем для дат из infobox (`1.0`).

Из этого источника обязательно исключаются:

- служебные разделы статьи (примечания/источники/литература/ссылки и их англоязычные эквиваленты — References/Citations/Bibliography/External links) — содержат даты обращения к источникам, не относящиеся к содержанию статьи;
- содержимое таблиц внутри раздела (например, таблица со списком стран — членов организации и датами их вступления) — табличные данные не являются «упоминанием в прозе» и дают систематический шум при обработке как обычного текста.

*Уточнения по факту реализации (2026-10-08):*
- Служебные разделы исключаются **вместе со всеми вложенными подразделами** (подраздел «Culture» внутри «External links» сам служебным не выглядит).
- Дата «день месяц год» с маркером эпохи (§16.2) сохраняется только годом (`-0044`, precision `year`) — раньше такие даты молча становились датами нашей эры.
- Американский формат «месяц день, год» («July 4, 1776») распознаётся с сессии 2б (2026-10-08); до этого статьи на американском английском не давали дат из текста (United States, Google, New York City). Даты в разделе возвращаются в порядке появления.
- **Известный шум:** основная масса дат приходит из пунктов списков, а не из абзацев (Гагарин: 423 даты в списках против 31 в абзацах; разделы наград, публикаций, «в культуре»). На корпусе 58% дат из текста относятся к 2000 году и позже. Отсекать такой шум — задача слоя отбора надёжных данных (`docs/PLAN.md`, сессии 3–4), а не extractor'а.

## 16.2. Поддержка дат до нашей эры (BCE)

Готового машиночитаемого представления для дат до нашей эры Wikipedia не предоставляет — ни в виде отрицательного года, ни в виде альтернативного `datetime`-атрибута. Требуется отдельный текстовый парсер, распознающий год с последующим маркером эпохи:

- Английская нотация: `BC`, `BCE`
- Русская нотация: `до н. э.`, `до н.э.` (с необязательными пробелами и точками), `до Р. Х.`, `до Р.Х.`
- Между числом и маркером эпохи может присутствовать дополнительное слово (например, `"81 год до н. э."`) — учитывается как необязательный элемент паттерна.
- Индикатор приблизительности (`c.`/`circa`, русское `около`) может присутствовать перед годом — не изменяет точность (`precision` остаётся `year`), поскольку модель `DatePrecision` не предусматривает отдельного уровня «приблизительный год».

**Для дат до нашей эры извлекается только год.** День и месяц в BCE-датах на практике часто представлены неоднозначно (например, диапазон дней: `"12 or 13 July 100 BC"`) — попытка однозначного разбора потребовала бы эвристик, выходящих за границы MVP (§4.3, «сложный NLP event extraction» явно исключён). Представление года — упрощённая (не астрономическая) числовая нумерация: год `N` до н. э. хранится как строка `-000N` (без смещения на единицу, применяемого в стандарте ISO 8601 для астрономической нумерации годов).

## 16.3. Модель `Event`

```json
{
  "id": "event-1",
  "date": "1879-03-14",
  "date_precision": "day",
  "title": "Born",
  "description": null,
  "source": "infobox",
  "confidence": 1.0
}
```

`date_precision` — одно из: `day`, `month`, `year`, `decade`, `century`, `unknown`. MVP реализует `day` (полная ISO-дата из infobox) и `year` (BCE-даты, оба источника — infobox и текст). Поддержка `month`/`decade`/`century` предусмотрена моделью, но не имеет реализованных путей извлечения на момент написания раздела.

## 17.2. Требуемые типы распознаваемых значений (по Roadmap Phase 4.5)

- целые числа (integer)
- десятичные числа (decimal)
- проценты (percentage)
- числа с единицами измерения (units)
- год (year) как отдельно распознаваемая категория числового значения
- числовые ряды (numeric series) — последовательности значений, пригодные для построения графика (`StatisticsChart`, Phase 6.7 Roadmap)

## 17.3. Ожидаемые архитектурные риски (на основе опыта реализации §12–§16)

Исходя из опыта работы с остальными extractors этой категории, при реализации `NumberExtractor` заведомо необходимо предусмотреть:

- проверку на обоих языках (en/ru) с самого начала разведки, а не постфактум — числовые форматы (разделитель разрядов, разделитель десятичных долей, обозначения единиц измерения) могут отличаться между локалями так же, как отличалась вёрстка infobox для дат (§16.1.1);
- ограничение источника данных так же строго, как это было сделано для дат (§16.1.1) — риск захвата чисел из служебных разделов (примечания, ссылки) и вспомогательных/навигационных таблиц аналогичен риску, уже дважды обнаруженному при реализации DateExtractor и TextDateExtractor;
- explicit различение чисел, извлечённых из infobox/таблиц (высокая точность, точная привязка к полю), и чисел, извлечённых из обычного текста статьи (если такое извлечение будет реализовано) — по аналогии с раздельными `date_extractor.py` / `text_date_extractor.py`, с соответствующей разницей в `confidence`.

*Состояние на 2026-10-08:* `number_extractor.py` реализован (Phase 4), источник — только инфобокс; группировка — префикс подписи «Группа — …». Риски, перечисленные выше, подтвердились на корпусе из 48 статей: из 355 чисел 148 без единицы измерения, 31 — на самом деле годы, 25 — коды и часовые пояса, многие «единицы» — случайные слова (`high`, `very`, `sq`); надёжны в основном проценты (55). Extractor по-прежнему не чистит этот шум: отбор пригодных чисел — задача слоя отбора надёжных данных (`docs/PLAN.md`, сессии 3–4). `StatisticsChart` (Phase 6) пока сам отбирает группы ≥ 3 значений в «%».

# 18. NLP Engine

В архитектуре должна существовать независимая абстракция:

```text
NLP Engine
```

NLP Engine принимает:

```text
NormalizedDocument
```

и может добавлять:

```text
tokens
lemmas
part_of_speech
morphology
dependencies
entities
relations
semantic_features
```

NLP Engine не должен зависеть от конкретного источника документа.

Например:

```text
Wikipedia
    ↓
NormalizedDocument ──┐
                     │
TXT ────────────────┤
                     ├──→ NLP Engine
Markdown ───────────┤
                     │
HTML ───────────────┘
```

Это является одним из главных архитектурных принципов проекта.

# 19. NLP analysis of user text

Функциональность анализа пользовательского текста планируется как последующее расширение.

Пользователь должен иметь возможность передать:

```text
TXT file
```

или непосредственно:

```text
plain text
```

После загрузки система должна:

1. определить формат;
2. прочитать текст;
3. создать `NormalizedDocument`;
4. разбить текст на предложения;
5. выполнить токенизацию;
6. выполнить морфологический анализ;
7. выполнить синтаксический анализ;
8. при включённом соответствующем модуле выполнить NER;
9. при наличии соответствующего модуля выполнить relation extraction;
10. сохранить результаты в единой модели;
11. определить доступные визуализации;
12. построить результат.

При этом пользовательский текст не должен проходить через Wikipedia-specific extraction.

# 20. Entity extraction from arbitrary text

В последующих версиях NLP Engine должен поддерживать извлечение сущностей из произвольного текста.

Например:

```text
Albert Einstein was born in Ulm in 1879.
```

может быть представлен как:

```json
{
  "entities": [
    {
      "type": "person",
      "label": "Albert Einstein",
      "source": "nlp"
    },
    {
      "type": "location",
      "label": "Ulm",
      "source": "nlp"
    },
    {
      "type": "date",
      "label": "1879",
      "source": "nlp"
    }
  ]
}
```

Визуализация этих сущностей должна использовать те же Widget API, которые применяются для данных Wikipedia.

**Смежное практическое наблюдение из уже реализованного:** извлечение дат из обычного текста Wikipedia-статей (§16.1.2, `TextDateExtractor`) — методологически родственная, но принципиально более простая задача: словарный поиск по названиям месяцев, без разбора смысла предложения. Она сознательно не квалифицирована как NER/relation extraction (§4.3) именно потому, что не пытается определить, _какое событие_ обозначает найденная дата — это и есть содержательная граница между допустимым в MVP паттерн-мэтчингом и полноценным NLP, описанным в этом разделе.

# 21. Provenance

Для каждого извлечённого объекта желательно сохранять происхождение:

```json
{
  "source": "nlp",
  "source_document": "document-001",
  "sentence_id": "sentence-004",
  "start": 15,
  "end": 30,
  "confidence": 0.94
}
```

Для Wikipedia:

```text
source = infobox
source = table
source = coordinate
```

Для пользовательского текста:

```text
source = nlp
```

Это позволит в будущем показывать пользователю:

> «Сущность обнаружена в предложении №4.»

и переходить к исходному фрагменту текста.

**Практическое состояние на момент написания:** полная модель provenance (с `sentence_id`, `start`/`end` смещениями в исходном тексте) не реализована. Реализованные extractors используют упрощённый вариант — поле `source` (§9 Entity model, тот же принцип применён к `Location`, `Event`, `Image`) и `confidence`, без точных текстовых смещений. Для `TextDateExtractor` (§16.1.2) роль грубой локализации играет заголовок раздела, где была найдена дата — это частичный, приближённый аналог полноценного provenance, реализуемый без NLP-инфраструктуры для разбиения текста на предложения.

# 39. Definition of Done для MVP

MVP считается готовым, если:

- пользователь вводит Wikipedia URL;
- URL валидируется;
- статья загружается;
- ошибки API обрабатываются;
- Infobox отображается;
- таблицы отображаются;
- координаты отображаются на карте;
- изображения отображаются;
- sections отображаются;
- базовые даты отображаются на Timeline;
- числовые ряды могут отображаться на графике;
- widget selector работает;
- результат получает UUID;
- результат хранится в Redis;
- результат имеет TTL;
- повторный запрос использует cache;
- страница адаптирована под mobile;
- проект запускается через Docker;
- есть базовые automated tests;
- есть README с инструкцией запуска.

Дополнительно архитектурно должно быть подтверждено:

- Wikipedia-specific слой изолирован от NLP;
- существует универсальная модель документа;
- источник данных является заменяемым компонентом;
- NLP Engine принимает нормализованный документ, а не Wikipedia HTML;
- Widget API не зависит от источника данных.

Полноценный пользовательский TXT-анализ для выполнения MVP не требуется.

# 42. Ключевая архитектурная идея проекта

WikiViz следует рассматривать не как систему:

```text
Wikipedia → visualization
```

а как систему:

```text
Various Sources
       ↓
Source Adapters
       ↓
Normalized Document
       ↓
Extraction / NLP
       ↓
Structured Knowledge
       ↓
Visualization
```

Wikipedia является первым и основным источником, на котором проверяется архитектура.

Пользовательский текст является одним из предусмотренных будущих источников.

Это позволяет постепенно перейти от:

```text
Wikipedia visualization
```

к:

```text
Universal text analysis and visualization platform
```

без необходимости переписывать существующую систему.

# 43. Архитектурное правило

Основное правило проекта:

> **Ни один downstream-компонент не должен зависеть от конкретного источника данных, если такая зависимость не является его непосредственной ответственностью.**

В частности:

```text
Widget
    ↓
Normalized Data
```

а не:

```text
Widget
    ↓
Wikipedia HTML
```

и:

```text
NLP
    ↓
Normalized Document
```

а не:

```text
NLP
    ↓
Wikipedia Article
```

Это правило должно учитываться при проектировании всех последующих компонентов.

Практическое подтверждение соблюдения этого правила к текущему моменту: все реализованные extractors (§11–§17) принимают на вход простую строку HTML статьи (`extract_tables(html)`, `extract_coordinates(html, article_title)`, `extract_images(html)`, `extract_dates(html)`, `extract_text_dates(html)`) — не Wikipedia-специфичный объект, не `RawArticle` целиком. Ни один из них не обращается к MediaWiki API напрямую и не содержит Wikipedia-специфичной сетевой логики — это подтверждает соответствие принципу «Source ≠ Extraction» (§3) уже на текущем этапе реализации, до формального появления `NormalizedDocument`/`Source Adapter Layer` как явных программных абстракций.
