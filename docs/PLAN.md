## Главный принцип следующего этапа

**Лучше не показать, чем показать мусор.** Извлекатели честно достают всё, что похоже на данные: таблицы, даты, числа, поля инфобокса. На пяти фикстурах уже видно, что часть этого — шум:

- даты публикаций и архивации в датах событий;
- годы с единицей «BC» и телефонный код в числах;
- навигационные таблицы «Preceded by / Succeeded by»;
- подписи картинок вместо значений инфобокса.

С любой страницы в визуализацию должны попадать только надёжные данные.

Отсюда новое звено конвейера:

```
Wikipedia → Extractors → Normalized Data → Отбор надёжных данных → Выбор виджетов → Виджеты
                          (всё найденное)     (правила, причины)     (простые правила)
```

Как разделены обязанности:
- **Извлекатели не цензурируют.** Они отвечают за точность разбора, а не за полезность данных: так разбор остаётся проверяемым, а ошибки не прячутся.
- **Отбор** — отдельный слой между данными и виджетами. Это и есть «Transformation» из принципа `Extraction ≠ Transformation ≠ Visualization`.
- **Виджеты получают уже отобранные данные.** Своей фильтрации у них нет: сейчас она есть в StatisticsChart, её нужно перенести в слой отбора.

Требования к правилам отбора:
1. **Работают на любой статье**, не только на пяти фикстурах. Правила — общие признаки (структура, единицы, повторы, размеры), а не исключения под конкретные статьи.
2. **Каждое отброшенное значение имеет причину** (например, «дата из раздела литературы», «таблица-навигация», «число без единицы и группы»). Причины видны на dev-странице: так правило можно проверить глазами и оспорить.
3. **Точность важнее полноты.** Если правило сомневается, данное не показывается. Это измеряется (см. сессию 3).
4. **Проверяются на корпусе статей**, а не на одной: правило, которое чинит одну статью и портит три другие, не принимается.

## Сессия 2. Проверка устойчивости (корпус статей)

**Цель:** узнать, как извлекатели ведут себя на статьях, которые мы не видели, пока исправления ещё дёшевы. Это и есть материал для правил отбора.

1. **Корпус 40–50 статей**, en и ru поровну, с закреплёнными ревизиями.
   - Отдельный манифест: например, `backend/tests/corpus/manifest.json`. Фикстуры frontend остаются как есть.
   - Состав — разные типы статей, по 3–5 каждого: персоны (современные и античные), страны, города, события и войны, организации, понятия, произведения, биологические виды, химические вещества, спортивные статьи, списки («List of …»), статьи без инфобокса, очень длинные и очень короткие.
   - Ещё 5–10 случайных статей (`Special:Random`): они проверяют, что правила не подогнаны под выбранные типы.
   - Список статей утверждает владелец до выгрузки.
2. **Скрипт прогона** (`backend/scripts/`, сеть, не в pytest): каждая статья проходит через нормализатор. По каждой собираются:
   - падения (исключения) — это ошибки, их надо исправить;
   - пустые результаты по каждому типу данных;
   - количества: разделы, таблицы, даты, числа, поля инфобокса, изображения, координаты;
   - **признаки шума**: слишком длинные ячейки и значения, числа без единиц, даты вне разумного диапазона, даты из служебных разделов, таблицы с пустыми ячейками, тексты ошибок шаблонов (Scribunto), повторы, изображения-значки.
3. **Отчёт** `docs/ROBUSTNESS_REPORT.md`, простым языком:
   - что падает и почему;
   - какой шум встречается и как часто;
   - где извлекатели теряют настоящие данные.

   Отчёт — исходный материал для сессии 3.
4. **Исправления в этой сессии — только падения.** Шум не чинится: для него пишутся правила отбора.

**Готово, когда:** корпус выгружен и воспроизводим, ни одна статья не роняет нормализатор, отчёт написан.

## Сессия 3. Критерии отбора надёжных данных: ТЗ (в чате, без кода)

**Цель:** `docs/SELECTION_TZ.md`, каталог правил отбора по типам данных. Опирается на отчёт сессии 2 и на пять фикстур.

**Что нужно решить владельцу:**

- **Где работает отбор.** Предлагается backend: отобранный результат сразу пойдёт в API и Redis (Phase 8–9). Frontend получает готовое, отбор не зависит от виджетов.
- **Что видно об отброшенном.** Предлагается так:
  - в пользовательской странице — ничего;
  - на dev-странице — список отброшенного с причинами;
  - в данных — отдельное поле с отброшенным и причинами или только журнал.

  Это изменение контракта, нужны варианты.
- **Насколько строго** отсекать в сомнительных случаях. Принцип «точность важнее полноты» требует числовой цели (например, «на выборке из корпуса не меньше 90% показанного владелец признаёт верным»).
- **Как проверять.** Владелец размечает выборку («верно / мусор») на dev-странице корпуса; по ней считается точность до и после правил.

**Каталог правил — заготовка, по которой ведётся обсуждение (уточняется по отчёту сессии 2):**

| Тип данных | Кандидаты в правила отбора |
|---|---|
| **Даты (Timeline)** | только инфобокс и текст основных разделов; убирать повторы одной даты из разных разделов; разумный диапазон лет; не показывать шкалу, если после отбора меньше 2 событий; годы-диапазоны («64–44 BC») не превращать в одно событие |
| **Таблицы** | исключать навигацию (succession box, «Preceded by / Succeeded by»), таблицы из 1 строки или 1 колонки, таблицы с большой долей пустых ячеек, тексты ошибок шаблонов; длинные ячейки-абзацы — признак, что это не таблица данных |
| **Инфобокс** | исключать значения-подписи к картинкам, служебные строки, слишком длинные значения; поле-родитель и его группа показываются один раз |
| **Числа (StatisticsChart)** | только группы с одной единицей измерения; не годы, коды и номера (телефонный код, ISO, «UTC+1»); разумные значения для единицы (проценты 0–100 и т. п.); группа ≥ 3 значений; правило переносится из виджета в слой отбора |
| **Изображения** | исключать значки и мелкие служебные картинки (иконки Wikidata, флажки размером с текст), повторы; ограничить число |
| **Координаты** | проверка допустимого диапазона, удаление повторов; карта — только если точки относятся к статье, а не к таблице-списку из сотни объектов (или наоборот — решить) |
| **Разделы (навигатор)** | служебные разделы (литература, ссылки, примечания) показывать в конце или не показывать — решить |

**Готово, когда:** у каждого типа данных утверждён список правил, способ показа отброшенного и цель по точности.

## Сессия 4. Отбор данных + Phase 7 (упрощённая)

**Phase 7 уменьшена.** Сложный движок правил, приоритеты, типы статей и «главный виджет» сейчас не делаются: по Roadmap это Phase 25 (Intelligent Widget Selection). Здесь остаётся:

1. **Слой отбора** по `docs/SELECTION_TZ.md`. Каждое правило — чистая функция с тестами (красный тест на шуме из корпуса, зелёный — на настоящих данных) и с причиной отбрасывания.
2. **Выбор виджета = есть ли у него отобранные данные.** `supports` смотрит на результат отбора. Порядок показа фиксированный, как сейчас в `setup.ts`. Пороги, которые сейчас живут внутри виджетов (StatisticsChart: ≥ 3 значений в «%»; Timeline: ≥ 2 событий), переезжают в слой отбора.
3. **Dev-страница корпуса:** по каждой статье видно, что показано, что отброшено и почему. Владелец размечает выборку и сверяет точность с целью из сессии 3.

Этим выполняется пункт MVP «widget selector работает» и Checkpoint C («система автоматически выбирает виджеты»).

**Готово, когда:** цель по точности достигнута на корпусе, ни одна статья корпуса не роняет конвейер, проверки зелёные, слито в `main`.

## Сессия 5. Phase 8 — тонкий сквозной путь

**Цель:** впервые пройти весь путь пользователя, пусть некрасиво. После этого проект — работающий сервис, а остальные фазы улучшают то, что уже работает.

- Backend: `POST /api/analyze` — URL → загрузка → нормализация → отбор → результат с UUID (пока в памяти; Redis — Phase 9).
- Frontend: страница с полем ввода URL и страница результата `/result/<uuid>` с отобранными виджетами.
- Минимальная обработка ошибок: неверный URL, статьи нет, Wikipedia недоступна.

**Решить заранее:** формат ответа API (отобранная модель + список виджетов?); что хранится в результате.

## Правила, которые действуют во всех сессиях

- Работа в ветке Claude Code, слияние в `main` через `git merge --no-ff`. После слияния владелец перепроверяет у себя: `pytest`, `npm run build`, `npx tsc --noEmit`, `npm test`, `/dev/widgets`.
- Только с решением владельца (вопрос на одну страницу с вариантами и рекомендацией): изменения контракта, новые зависимости, вид виджетов, правила отбора.
- ТЗ v3.1 и Roadmap не меняются без отдельного решения владельца.
- В конце каждой сессии обновить `docs/PROGRESS.md` (состояние, решения, техдолг) и этот план.
