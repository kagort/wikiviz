## Где мы относительно MVP (ТЗ §39)

| Требование MVP | Состояние |
|---|---|
| Infobox, таблицы, карта, изображения, sections, Timeline, график | **готово** (Phase 6), пока только на dev-странице |
| widget selector работает | частично: выбор по `supports`, без правил и приоритетов → **Phase 7** |
| пользователь вводит URL; URL валидируется; статья загружается | нет пользовательской страницы и API → **Phase 8** |
| ошибки API обрабатываются | частично (ошибки клиента есть) → **Phase 11** |
| результат получает UUID, хранится в Redis, имеет TTL, повторный запрос использует cache | нет → **Phase 8–9** |
| страница адаптирована под mobile | нет (страницы намеренно без стилей) → **Phase 14** |
| проект запускается через Docker | частично (Dockerfile backend есть) → **Phase 14** |
| базовые automated tests | есть (192 + 168) → **Phase 12–13** расширят |
| README с инструкцией запуска | устарел («Phase 0») → **Phase 14** |

## Сессия 1. Хвосты Phase 6 (короткая)

**Цель:** закрыть найденное при визуальной проверке, пока контекст свежий.

0. **До сессии, у владельца:** диагностика карт (`PROGRESS.md`, раздел 4) — `/dev/map`, код ответа тайлов в F12, прямая ссылка на тайл с VPN и без. Результат принести в сессию.
1. **Карты:** если диагностика покажет, что виноват адрес, заменить `{s}.tile.openstreetmap.org` на `tile.openstreetmap.org`. Если виновата VPN — записать в `PROGRESS.md` как особенность среды; код не трогать.
2. **Таблицы-навигация (succession box)** у Цезаря: разведка разметки (классы), предложение владельцу (исключать или нет), затем красный тест → исправление.
3. **Инфобокс:**
   - пропускать строки с изображением под заголовком (Токио, «Символика — Флаг префектуры»);
   - убрать «:,» при склейке списка (Цезарь, Conflicts).
4. **Вид InfoBox:** повтор «поле-родитель + подзаголовок» (France, Government). Предложить 2 варианта, решает владелец.
5. **Мелкий техдолг:**
   - BOM в 12 файлах — пересохранить в UTF-8 без BOM;
   - `README.md` — актуальный статус и инструкция запуска.
6. По желанию владельца: «Introduction» для русских статей («Введение»). Это меняет данные, поэтому решает владелец.

**Готово, когда:** все проверки зелёные, фикстуры перевыгружены (повторный запуск без diff), `PROGRESS.md` обновлён, слито в `main`.

## Сессия 2. ТЗ на Phase 7 (в чате, без кода)

**Цель:** `docs/PHASE7_TZ.md` — что именно должен делать Widget Selector. Это Checkpoint C: «система автоматически выбирает виджеты».

Вопросы, которые нужно решить владельцу:
- **Что решает селектор.** Только «показывать или нет», или ещё порядок и приоритет? Ограничение числа виджетов? Главный виджет страницы?
- **Правила.** Примеры: «у статьи о человеке Timeline выше Map», «таблица из одной строки не показывается», «StatisticsChart только при ≥ N значениях». Где задаются: в коде или декларативно (таблица правил)?
- **Где работает селектор:** на frontend (как сейчас `selectWidgets`) или на backend (вместе с результатом для Phase 8)? ТЗ §3: Selector стоит после Normalized Document и не зависит от источника.
- **Тип статьи** (человек, страна, город, язык программирования). Нужен ли он селектору и откуда берётся — по полям инфобокса, без NLP (NLP вне MVP)?
- **Как проверять:** ожидаемый набор и порядок виджетов для каждой из пяти фикстур как приёмочный тест; возможно, ещё 2–3 статьи другого типа.

Ограничение из Phase 6: `registry.ts` и `selector.ts` не менялись, правило «виджет — одна строка» (Rule 6) сохраняется.

## Сессии 4+. Phase 8–14 — путь к MVP

Каждой фазе предшествует короткое ТЗ (в чате), затем реализация (Claude Code).

| Фаза | Суть (по ТЗ §39) | Что решить заранее |
|---|---|---|
| **8. Result System** | API `/api/analyze`: URL → загрузка → нормализация → результат с UUID; пользовательская страница: поле ввода URL и страница результата `/result/<uuid>` | формат ответа API; что хранится в результате (модель + выбранные виджеты?) |
| **9. Cache** | Redis: результат по UUID с TTL; повторный запрос той же статьи берётся из кэша | длительность TTL; ключ кэша (URL? URL + ревизия?) |
| **10. Security** | валидация URL (только `*.wikipedia.org`), ограничение частоты запросов, закрыть `/dev/*` в продакшене; разобрать 3 отложенные уязвимости npm | какие языковые разделы Wikipedia разрешены |
| **11. Error Handling** | понятные сообщения: нет статьи, неверный URL, Wikipedia недоступна, превышено время | тексты сообщений, язык интерфейса |
| **12. Test Corpus** | набор статей разных типов с закреплёнными ревизиями (расширение `manifest.json`) | какие статьи и типы (персоны, страны, города, события, понятия; en и ru) |
| **13. Automated Testing** | прогон пайплайна по корпусу, проверки в CI (GitHub Actions?) | нужен ли CI и где |
| **14. MVP** | стили и мобильная вёрстка, Docker Compose (frontend + backend + Redis), README | минимальный дизайн; Tailwind уже в стеке |

## Правила, которые действуют во всех сессиях

- Работа в ветке Claude Code, слияние в `main` через `git merge --no-ff`. После слияния владелец перепроверяет у себя: `pytest`, `npm run build`, `npx tsc --noEmit`, `npm test`, `/dev/widgets`.
- Изменения контракта, новые зависимости, вид виджетов — только с решением владельца (вопрос на одну страницу с вариантами и рекомендацией).
- В конце каждой сессии обновить `docs/PROGRESS.md` (состояние, решения, техдолг) и этот план.
